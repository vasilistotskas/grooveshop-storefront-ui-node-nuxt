# Nitro runtime

Server middleware, plugins and logging. The Django proxy contract is in
`.claude/rules/server-routes.md`.

## Server Middleware

Numeric prefixes order execution. Request logging is via evlog (there is no `log.ts`).

- `0.anonymous-session.ts` — answers nuxt-auth-utils' `GET /api/_auth/session` with `{}` for a visitor without a session, which the module's own handler would mint (see `.claude/rules/auth.md`)
- `0.markdown-negotiation.ts` — serves the `.md` variant of a route when an AI/agent client negotiates for it (`@nuxtjs/seo`'s AI Ready)
- `0.redirects.ts` — 301 redirect from `www.` to non-www
- `0.request-id.ts` — `x-request-id` on `/api` responses (see Structured Logging)
- `0.tenant.ts` — resolves `event.context.tenant` from the request host (before every middleware that reads it; see Multi-Tenant Architecture)
- `1.ai-ready-gate.ts` — gates the on-demand `.md`/llms routes
- `1.device-class.ts` — stamps the User-Agent's device class (`mobile`/`tablet`/`desktop`, `shared/utils/deviceClass.ts`) as the `x-device-class` request header, overwriting any client value, which the cached page rules vary on
- `1.tenant-epoch.ts` — stamps the store's tenant-config epoch as `x-tenant-epoch`, which the cached page rules vary on (see Multi-Tenant Architecture)
- `1.locale.ts` — `event.context.locale` = the page's locale: the path prefix of a page request, or the `X-Language` the app's fetchers state on an `/api` request, clamped by `servedLocale` (`shared/i18n/tenantLocales.ts`). No cookie, `Accept-Language` or `?locale=` source. It is sent to Django as `X-Language` and is part of every `tenantCacheKey`
- `2.evlog-auth.ts` — attaches the auth session user id to the wide event (`event.context.log`)
- `2.evlog-client.ts` — sets `client` on the wide event (see Structured Logging); nothing for a request without a User-Agent
- `2.evlog-ingest-rate-limit.ts` — rate limit, per client IP and store, on evlog's browser-log ingest, `POST /api/_evlog/ingest`
- `3.csp.ts` — per-tenant Content-Security-Policy (extends src lists with the tenant's `allowedCspSources`)
- `5.tenant-canonical.ts` — canonical host enforcement for the tenant's primary domain
- `6.indexnow-key.ts` — serves the store's IndexNow key file, `/<key>.txt`, while `TenantConfig.indexnowKey` is set
- `6.tenant-favicon.ts` — serves the tenant's favicon

## Server Plugins

One file per concern in `server/plugins/` (each documents itself); those with cross-cutting contracts:

- `http-agent.ts` — Undici Agent for connection pooling (100 connections, no pipelining (`pipelining: 1`), keep-alive 30s) — reduces latency for internal API calls
- `edge-cache.ts` — lets Cloudflare cache ONLY the pages Nitro served from its page cache: `Cloudflare-CDN-Cache-Control` (never `s-maxage`, which disables the edge's stale-while-revalidate), `Cache-Control: no-cache` for browsers, and `Cache-Tag: storefront-html,storefront-html-<schema>` — tag names are a contract with Django's `core/cache/edge.py`, which purges them after an edit and after a deploy. Every other page (an HTML document or `_payload.json`: personal pages, and errors, which Nitro stamps with `s-maxage` although it never caches them) gets `Cache-Control: private, no-store`, and so does every `/api` GET that states no caching of its own and every `/api` error (`isPrivateApiResponse`: without a `Cache-Control` a browser may keep a 404 or 410 and replay it); redirects keep theirs. No cookie rule is needed at the edge: what it stores is what Nitro already replays to every visitor, signed in or not. Set as the response ENDS, because h3's 304 revalidation is sent from inside Nitro's cached handler. Rules in `server/utils/edgeCache.ts`. A render that fell back to defaults (`event.context.degradedRender`, set by `markDegradedRender` when the store's texts or theme could not be loaded) answers with status 503 while it is inside Nitro's page cache, which stores nothing below 400; this plugin puts the real status back as the response ends and marks it `private, no-store` (`shared/constants/degradedRender.ts`)
- `tenant-theme.ts` and `tenant-fonts.ts` — the store's `<style id="tenant-theme">` and the font faces it keeps, both from the theme document of the store's current release (`requestStoreTheme`, `server/utils/storeTheme.ts`): `themeCss(settings, design)` (`shared/theme/compile.ts`, the compiler the editor's preview draws with) writes every token, Nuxt UI's `--ui-primary` and the three colour scales included, over `#nuxt-ui-colors` (which keeps the app config's platform palettes on server and client alike, so nothing flashes or mismatches). The read is `GET builder/published`'s `theme`, validated against `zThemeSettings`, cached as the function `builderTheme` (5 min, `swr: false` so a superseded entry expires; key = store, language, epoch) and read once per request. A store with no published theme gets `themeDefaultsFor(design)`. A read that fails does too, and the render is marked degraded (`markDegradedRender`: kept out of Nitro's page cache, the edge and the browser, so the wrong colours outlive nothing). `render:html` runs on a page-cache miss only, and its hooks may await. A release moves the store's epoch (the `builder` surface's `invalidates_tenant_config`), so `builderTheme` needs no purge of its own name; not on the page editor (`isBuilderEditorPath`). The same plugin writes the page's `theme-color` (`themeColorOf`: the light scheme's accent; `PLATFORM_THEME_COLOR` where there is no theme to draw with, the editor and a page with no store), and `/manifest.webmanifest` names that colour as `theme_color` through the same `requestStoreTheme`. `test/fixtures/builder/theme-published.json` holds the production themes and `theme-rendered.json` what those stores painted before they had one (`compile.spec.ts`)
- `storage.ts` — Configurable cache backend: tests Redis connectivity, falls back to memory driver if unavailable. The Redis mount namespaces keys by build id, sweeps superseded builds, and stores values over 1 KiB brotli-compressed behind a `br:` marker (`withCompressedValues`), transparent to every cached route, handler and function; shorter values (rate-limit counters, tenant epochs) are stored plain
- `tenant-site-config.ts` — the store's own `@nuxtjs/seo` site config (url, name, per-locale description) through nuxt-site-config's `site-config:init` hook, which runs whenever a request's site config is first built, before any route middleware. A route middleware was too late: nuxt-ai-ready builds its `Link` header ahead of every middleware and serves `/llms.txt` and the `.md` mirrors on paths `0.tenant.ts` bypasses, so they named the platform's URL. On a store that does not serve those surfaces (`servesAiSurfaces`, `server/utils/aiSurfaces.ts`) the `Link` header loses its links to them as the response ends
- `server/early-plugins/runtime-config.ts` — NOT in `server/plugins/`: registered via `nitro.plugins` in `nuxt.config.ts` so it runs before every module's plugin. Seeds each request's `useRuntimeConfig(event)` with a clone of the boot-resolved config, skipping Nitro 2's per-request env re-walk (63% of a trivial request's CPU, ~19% of a page render). Keep it first; a copy built by an earlier `request` hook makes it a no-op.
- `startup-validation.ts` — Validates required env vars (`NUXT_APP_SECRET` >= 32 chars, the backend URLs) at startup; fails hard on misconfiguration

## Structured Logging (evlog)

Uses `evlog/nuxt` module for structured logging. `log` is auto-imported on both client and server (Nitro).

- **Simple logging**: `log.info('tag', 'message')` (2 args max — evlog silently drops a third context arg), or the wide-event object form for context: `log.info({ tag: 'tag', message: 'message', ...context })`, `log.error({ action: 'name', error })`
- **Wide events** (server only): `event.context.log?.set({ key: value })` in routes and middleware (evlog's `useLogger(event)` is typed on h3's event, so `nuxt/server` code reads the logger from the context, where evlog puts it) — one rich event per request, auto-emitted at request end
- **What reaches the log line**: only fields set on the request logger BEFORE it emits — `server/middleware/0.tenant.ts` (`tenantSchema`, `tenantName`), `server/middleware/2.evlog-auth.ts` (user id), `server/middleware/2.evlog-client.ts` (`client`: browser + major version, OS name, render `deviceClass`, `bot`, `country`). evlog prints the stdout line (what Vector ships to VictoriaLogs) at emit; `evlog:enrich` hooks run after that and feed drains only, and there is no drain, so never add an `evlog:enrich` hook expecting it in a SERVER event's line. Browser events (`/api/_evlog/ingest`) are the exception: evlog redacts, samples and enriches them BEFORE it prints, so `server/plugins/evlog-client-context.ts` names their store and their `client` (the same `clientFacts` as server events: browser + major version, OS name, `bot`, `country`) in an `evlog:enrich` hook. Those events are sampled by the same `sampling.rates` as server ones. `silent` + an `evlog:drain` hook is not the way out either: only request events reach that hook, so every other `log.*` line (errors included) would vanish. Never log the raw User-Agent or an OS version (browsers freeze it).
- **Every request is logged** except the assets a page pulls (`evlog.exclude` in `nuxt.config.ts`): page renders and `_payload.json` included. In VictoriaLogs a storefront event's path is its `_msg` (the `VL-Msg-Field` fallback), not a `log.path` field.
- **Sampling**: Production-only via `$production.evlog.sampling` in `nuxt.config.ts`
- **Client-error log level**: evlog logs every *errored* request at `error` level (`level = manualLevel ?? hasError ? 'error' : …`), with no 4xx/5xx distinction — so benign client errors (unknown-route 404s, allauth 401 "not authenticated, here are your flows") drown out real 5xx faults. `server/plugins/evlog-client-error-level.ts` downgrades 4xx → `warn` via a Nitro `error` hook + `useLogger(event).setLevel('warn')` (`isClientError` in `server/utils/http-status.ts`); 5xx stays `error`. 4xx remain visible via the `evlog.sampling.keep: [{ status: 400 }]` rule. Mirrors evlog's own Datadog severity mapping.
- **Browser error reports** (`app/plugins/error-reporting.client.ts`, `app/utils/clientErrors.ts`): every hook (`vue:error`, `app:error`, `app:chunkError`, `window` error, `unhandledrejection`) goes through `createClientErrorReporter`, which sends PLAIN DATA `{ action: 'client:<source>', error: { name, message, stack (first frames), statusCode?, statusMessage? }, info? }`. evlog's client logger serialises an `Error` only when it is the top-level argument (`log.error(err)`, which would drop our `action`); an `Error` nested in an event reaches the ingest as `{}`. URL query strings and fragments are dropped from message and stack. A chunk the visitor's browser could not download (`isChunkLoadError`: Chrome "Failed to fetch dynamically imported module", Firefox "error loading dynamically imported module", Safari "Importing a module script failed.", Vite "Unable to preload CSS") goes out at `warn`, together with Vue's runtime-13 async-loader error it causes, and so does a `fetch` that got no response at all (`isNoResponseError`: Chrome "Failed to fetch", Firefox "NetworkError when attempting to fetch resource.", Safari "Load failed" / "A network error occurred.", whole message only), so `GrooveShopLoggedErrors` counts only what we must fix; everything else stays `error`. Both patterns live in `shared/utils/connectionFailure.ts`, and the ingest applies the same rule to every OTHER browser event: a store or component site's own `log.error({ action, error })` whose error or `cause` is one of them, with no status, is printed at `warn` (`warnOnConnectionFailure` in `server/utils/clientEventLevel.ts`, called by `server/plugins/evlog-client-context.ts` before redaction), so no call site has to classify it. Browser notices nobody can act on (`isBrowserNoise`: ResizeObserver's loop notice, Android in-app browsers' "Java object is gone") are not reported at all. On a browser that cannot run the page (`browserCannotRunPage`: the page has Nuxt's `#entry` import map and the browser reads none, i.e. Safari before 16.4) every report goes out at `warn` with `unsupportedBrowser: true`: no lazy chunk loads there, so its "#entry" and "$routeBaseName is not a function" errors are one cause. The import map stays on, by the owner's choice (2026-10-16); a build target that lists such a browser would make Nuxt drop it. A store call site's own `log.error({ action, error })` nests the `Error`, which evlog serialises in the browser as `{ name, message, stack, cause, status, statusText, statusCode, data }`: a failed `$api` call carries its status AND the response body (`data`, Django's body), checked on 2026-10-19 against the installed serializer. A field error can echo what the customer typed, so `server/plugins/evlog-client-context.ts` (the one place every browser event passes, before evlog prints it) reduces that body with an ALLOWLIST (`server/utils/clientEventRedaction.ts`): only field names, `code` / `reason` / `type` / `param` holding an identifier, and `status` / `statusCode` / `statusText` survive; every other value, of any type (string, number, boolean, bigint, null, list, object), becomes `<redacted:body>`. Never add a type or a key to a deny list. Its response headers are not part of that, so a site that wants the request id adds `requestId: requestIdOf(error)` (`shared/utils/error.ts`), as `Product/Review.vue` does; `serializeClientError` does it for the global hooks. **The request id**: `server/middleware/0.request-id.ts` returns evlog's `requestId` (the `X-Correlation-ID` Django receives) as `x-request-id` on every `/api` response (the bare `/api` too, as evlog treats it as an API path), errors and the 404/503 of `0.tenant.ts` included, and on nothing else: a rendered page is replayed from Nitro's page cache and Cloudflare's edge to many visitors, and an id belongs to one request. A cached API handler replays its own inner event's headers, so a visitor gets their own id, never the one that filled the cache (`test/e2e/requestId.ts`).
- **Browser INP reports** (`app/plugins/web-vitals.client.ts`, `app/utils/inpReport.ts`): a page whose INP is not good (over 200 ms) sends ONE `warn` event `{ action: 'client:inp', inp: InpReport }` when it is hidden: web-vitals' attribution (target selector, route NAME never path, the three phases, the longest long-animation-frame script by `/_nuxt/` path or origin + path, never a query; the page's own inline code is `document`). `redactClientInpReport` in `server/utils/clientEventRedaction.ts` rebuilds `inp` from the `InpReport` fields (`shared/types/inpReport.ts`), each checked against its shape; add a field to all three or it is dropped. Query them in VictoriaLogs with `action:client:inp`.
- **ESLint**: `no-console: 'error'` enforced — use `log.*` instead of `console.*`
- **Scope limitation**: `log` is NOT auto-imported in `i18n/` directory (outside Nitro/Nuxt auto-import scope)
