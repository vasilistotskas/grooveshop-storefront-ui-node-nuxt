# Nitro server layer

The Django proxy contract and the generated OpenAPI code. Server middleware, plugins and logging are in `.claude/rules/server-runtime.md`.

## Backend Communication Pattern

The Nuxt server acts as a **proxy** to the Django backend. Client-side code calls `/api/...` routes on the Nuxt server, which then forwards requests to the Django API (`NUXT_API_BASE_URL`).

- **Server API routes** (`server/api/`): Proxy endpoints organized by domain — products, cart, orders, blog (posts/comments/categories), user (account/addresses), search, loyalty, notifications, subscriptions (topics/user), contact, countries, regions, pay-way, settings, health, websocket
- **Server API pattern**: Routes use `getValidatedQuery`/`readValidatedBody` (from `nuxt/server`, given the Zod schema itself) and `parseRouterParams` for input, `useBackendFetch(event)` to Django, `parseDataAs` for response validation, `return handleError(event, error)` for error handling: an upstream 4xx with a body is returned verbatim with its status (the client's `error.data` is Django's body, whichever route it called), every other failure is thrown and a 5xx body never reaches the browser unless the route documents it (`forwardUpstreamDocumentedError`). Cached routes use `defineCachedRoute` (Nitro's cache, SWR) — see "Server code and Nuxt 5".
- **`server/utils/backendFetch.ts`**: every Django call goes through `useBackendFetch(event)` (or `backendFetchFor({ tenantHost, locale })` in a cached function, which has no request): an explicit ofetch instance that adds `X-Forwarded-Proto`, the store's `X-Forwarded-Host`, `X-Language`, the visitor's identity and the correlation id, to Django origins only (`isInternalBackendUrl`). There is no global `$fetch` on the server and nothing patches one.
- **`server/utils/auth.ts`**: Creates forwarding headers (`X-Session-Token`, `Authorization`, `X-Forwarded-Host`) for Django requests; `createHeaders(event, …)` sets `X-Forwarded-Host` to the store the request is for (`requestTenantHost`, never a client-sent `X-Forwarded-Host`); `processAllAuthSession(event, …)` handles token propagation. Every helper takes the request explicitly.
- **`server/utils/tenantHost.ts`**: `server/middleware/0.tenant.ts` resolves the store's host once (`resolveTenantHost`) into `event.context.tenantHost`, before its bypass checks; `requestTenantHost(event)` reads it there, so it serves a route's event and the h3 event Nitro gives cache keys and plugins alike
- **`server/utils/api.ts`**: `createCachedFetcher<T>` for paginated data fetching with caching
- **`server/utils/cartSession.ts`**: Cart session management via `useCartSession(event)` — keeps `cartId` in nuxt-auth-utils' session (the signed-in user's `nuxt-auth-session` cookie, written with the cart's 30-day lifetime) plus a plain `cart-id` spare cookie; provides `getCartHeaders`/`handleCartResponse`/`clearCartSession`; `getCartHeaders` sets `X-Forwarded-Host` the same way as `createHeaders`
- **`server/utils/parser.ts`**: `parseDataAs(data, zodSchema)` for runtime validation of API responses
- **`server/utils/error.ts`**: `handleError(event, error)` (forwards an upstream 4xx body; throws request validation, response contract, 5xx and HTTP errors), `handleAllAuthError(event, error)` (auth-specific errors with session management; always throws, and the allauth client reads its wrapper at `error.data.data`)
- **`server/utils/oauth.ts`**: Shared OAuth helpers (`captureOAuthProcess`, `readAndClearOAuthProcess`, `storeOAuthTokensAndRedirect`, `redirectOAuthError`) used by Google and Facebook route handlers
- **`app/utils/auth.ts`** (client): `callAuthChangeHook` → `nuxtApp.callHook('auth:change')` — the only path for auth state changes; composable `onResponse`/`onResponseError` interceptors call this
- **Guest order access**: Guest order API calls require a `?uuid=` query parameter for Django's `IsOwnerOrAdminOrGuest` permission check. Server routes under `server/api/orders/[id]/` forward the UUID to the backend.

## Server code and Nuxt 5

Nuxt 5 runs Nitro v3, which has no server auto-imports and no global
`$fetch`. The server is written for it now:

- **Routes and middleware import from `nuxt/server`** (`defineEventHandler`,
  `getValidatedQuery`, `readValidatedBody`, `createError` with
  `status`/`statusText`, `sendRedirect` — which RETURNS the body to respond
  with — `getRouterParam(s)` with `{ decode: true }`, `useRuntimeConfig()`
  without an event) and use web APIs on the event: `event.url`,
  `event.req.method`, `event.req.formData()`, `event.res.headers`.
- **Nitro-only APIs are imported from `nitropack/runtime`** (Nuxt 5 renames
  these to `nitro/*`): `defineNitroPlugin`, `defineCachedFunction`,
  `useStorage`, `useEvent`. Server plugins are Nitro code and use h3's
  helpers on the h3 event Nitro gives their hooks.
- **Cached routes use `defineCachedRoute(handler, options)`**
  (`server/utils/cachedRoute.ts`): Nitro's cache around a `nuxt/server`
  handler. Its `getKey` gets h3's event: read the query
  with h3's `getQuery`, params with `nuxt/server`'s `getRouterParam(s)`,
  and the store and locale from the context (`tenantCacheKey`). Its
  `shouldBypassCache` gets the portable event, like the handler, so it can
  ask the same `server/utils` the handler does (`shipping/options.get.ts`
  skips the cache for a request that names a cart). A cached handler sees
  only the request headers its `varies` names, even on a bypassed request;
  with a custom `getKey`, `varies` does not key the entry.
- **evlog's wide-event logger is `event.context.log`** (typed in
  `shared/types/request-context.d.ts`); evlog's `useLogger` is typed on h3's
  event only.
- **h3 handlers remain only where a module or h3 itself requires them**:
  the OAuth routes (nuxt-auth-utils' factories),
  the RSS feed, the manifest, `handlers/custom-page.ts`, `1.device-class.ts` and `1.tenant-epoch.ts` (each writes a Node
  request header for Nitro's cache `varies`) and `contact/attachment.post.ts` (`proxyRequest`
  streams the upload).
- `test/unit/source-rules/server-imports-are-explicit.spec.ts` fails on any
  h3 or Nitro name used in `server/**` without an import.

## Server Routes

- `server/routes/auth/google.get.ts` and `facebook.get.ts` — OAuth callback handlers (store tokens in encrypted session, not URL params)
- `server/api/auth/oauth-params.get.ts` — One-time-use endpoint that reads OAuth params from session and clears them
- `server/handlers/rss-feed.ts` — the store's feeds (`RSS_FEED_PATHS`, `shared/constants/feeds.ts`), registered in `nuxt.config.ts` (`nitro.handlers`) as static routes under every locale prefix (`withLocalePrefixes`: a `[locale]` param route loses to the `/en/blog/**` page rule) and built by `server/utils/rssFeed.ts`: `/rss.xml` blog posts plus, with the catalogue, products; `/blog/rss.xml` posts only; `/<locale>/…` in a language the store serves, its links in that language, 404 for one it does not. Every cached read is a function named `rss:<what>` with `swr: false` (an SWR entry is served stale without an age limit and kept without a TTL), purged by Django's `sitemap_seo` surface (`cache:nitro:functions:rss*`) on every content change and go-live. A feed carries `edgeCacheHeaders` (the store's Cache-Tag), so Django's store purge reaches Cloudflare's copy. The cache key carries the tenant-config epoch. The blog feed opts out of the `/blog/**` page cache (`cache: false` in `nuxt.config.ts`, every locale). A 404 (blog off, unserved language) and a 500 are `private, no-store`. `setupPageHeader` advertises the feeds in the page's language (`rel="alternate"`, titles `feeds.store` / `feeds.blog`)
- `server/plugins/sitemap-store-urls.ts` and `server/utils/sitemapStoreUrls.ts` — the store's own sitemap URLs (posts, products, categories, content and custom pages), added in-process by the `sitemap:sources` hook inside the `/sitemap.xml` request, not as an HTTP source. A read that fails (a cold cache during a Django outage; the reads are `swr`, so a warm one serves its last good list) leaves its URLs out and marks the response (`markSitemapIncomplete`, `server/utils/sitemapIncomplete.ts`): 503 with a `Retry-After`, so the `/sitemap.xml` route rule keeps its last good sitemap and nothing caches the incomplete one. `server/plugins/sitemap-tenant-gate.ts` marks it the same way when its content or layout read fails. `test/e2e/sitemapOutage.ts` holds it on a real server
- `server/api/builder/pages/[pageKey].get.ts` — a published page ready to render, in two halves cached APART. (1) The DOCUMENT: Django's `GET builder/published/<key>?locale=` (the current release's page, resolved for the language: overlay merged, disabled nodes dropped) through `parseBuilderPage` (`parseDocument(.., 'page')`), cached as the FUNCTION `readPublishedPage` (`server/utils/builderPageDocument.ts`, name `builderPageDocument`, key `dataCacheKey`: store, language, epoch, page; 5 min + 1 h stale): Django's `builder` surface purges that name and the page routes after a release, so renaming it stops a publish reaching visitors until the TTL runs out. It holds the page's own content and none of what the page shows from the store's data. `{ page: null }` is Django's 404 `page_not_published`, the normal state of a page the store has not built: data, so it is cached (any other 404, and every 5xx, propagates, so an outage is never taken for an unbuilt page). (2) What depends on the store NOW, per request (`renderBuilderPage`): the data settings read and applied (`resolveBuilderData`, below), the links answered as the addresses they have now (`resolveLinks`, from `readLinkTargets`; a link to a record that is gone, an unpublished page, or a page a switched-off store feature takes away (`blockedFeaturePaths`, the gated routes' one table: `/blog` or a post with the blog off, a product with the catalogue off, a published page whose address is one of them, such as the store's own blog page) is taken out, so the component draws no button rather than a 404), and each section as `{ id, componentType, props }` (`sectionProps`). `componentType` is the block type without its version, the key of `componentRegistry`; `props` is exactly what the unchanged section component gets, so the client holds no block definition and no Zod. The route itself is NOT cached (a plain `defineEventHandler`; `edge-cache.ts` marks it `private, no-store`), so a price or a name never freezes inside a cached page. The only reader of page content: `useBuilderPage` (`app/composables/useBuilderPage.ts`) wraps it for every page body of both designs (sections, the page's `seoTitle` / `seoDescription` at high head priority, each in the page's language or else the default language's (Django lays the translation over the default settings), and its `heading`, the h1 `Home.vue` draws in place of the store's name in both designs; the editor's page-settings panel, `Builder/PageSettings.vue`, writes all four).
- `server/utils/builderData/` and `shared/builder/data.ts` — the data settings of a block (`builderField.ref(kind, { onMissing })`, `builderField.query(source, { onEmpty, maxLimit })`; `defineBlock` derives the block's `data` from the schema, the catalogue states it per block when there is any) and the ONE resolver that reads them. A `ref` stores a record id, a `query` a descriptor (`shared/builder/dataSources.ts`: closed objects per source, `mode: 'picked'` the merchant's ids in the merchant's order, `mode: 'filter'` a rule; every key maps to a filter or ordering the Django list endpoint has). `dataSites` lists the settings a page draws, `planData` merges them into the fewest reads (every id of a kind in ONE set, each distinct list once by its canonical descriptor), `readData` runs them in parallel through `RECORD_LOADERS` / `QUERY_LOADERS` (`loaders.ts`: one `cachedRead` per Django list endpoint, cached as the function `builderData<Kind>` under the store, language, epoch and the Django query itself, `DATA_CACHE_SECONDS` with `swr: false` so the entry expires from storage), and `applyData` replaces each setting by `ResolvedRef` / `ResolvedQuery` under the same name: the component never sees the stored id or descriptor and never fetches. A kind or source whose store feature is off (`DATA_FEATURES`: products and categories need `catalogue`, posts and blog categories `blog`, offers `promotions`) is not read at all, since Django refuses it and a refused read is not cached: its records are absent and its lists empty, as for a record that is gone (a hero's product on a store without a catalogue). `hide` takes out the node (the list entry, for a setting inside a list) that holds a setting with nothing to show, `empty` hands the component its status; a read that failed is `failed`, kept apart from an absence, and never hides anything. The published page (`renderBuilderPage`), the editor's preview (`keepHidden`: the canvas keeps what the page would leave out) and a share link all go through `resolveBuilderData`. **TRANSITIONAL (P15 stage 2, deleted at stage 4):** the seven image blocks (`hero_banner`, `hero_slide`, `gallery_image`, `media_text`, `trust_badge`, `testimonial`, `hero_carousel`) have a `media` ref beside their old URL setting, and `resolveBuilderData` ends with `legacyImageRefs` (`server/utils/builderData/legacyImages.ts`, on every page, data sites or none): a node with the old setting and no new one gets `{ status: 'ok', value: { path, alt } }` under the new name, a node whose new setting is present ignores the old, and the old settings (and the old alt) are always taken out of the props. Components read `ResolvedImage` (`readyImage`, `app/utils/builderImage.ts`) and never a URL; a `missing` or `failed` image draws the component without one. What the adapter reads is each block's `legacyImages` declaration (`defineBlock`; see `nuxt-modules.md`). The cache names are a contract with Django's purge. `test/fixtures/builder/data-cases.json` is the shared vector set (Django vendors it).
- `server/api/builder/navigation.get.ts` — the chrome's menus: `GET builder/published` (the release's groups and its page list) plus the store's published content pages (`publishedContentLocalesForHost`), each group through `parseDocument(.., 'group')` and `navigationItems`, answered as `NavigationItems` (`shared/types/navigation.ts`); a slot the store has not built is absent, which `useNavigation` reads as the built-in menu. A link to a page or content page that is not published is hidden and a footer column emptied with it. It fails instead of answering when either read fails (a menu that hides the wrong links must not be cached). Cached as the handler `builderChrome`, same purge as `builderPage`. `publishedPagesForHost` (`server/utils/tenantSetting.ts`) reads the same release page list for the sitemap source and the sitemap tenant gate (`pages: [{ key, kind, updatedAt }]`), failing closed.
- `server/api/builder/session.{post,get,delete}.ts` and `server/utils/builderSession.ts` — the page builder's STAFF session on the store host. Django's admin ("Edit storefront") mints a single-use ticket and sends the browser to `/_builder?ticket=`; `POST /api/builder/session` `{ ticket }` exchanges it server to server (`useBackendFetch`, `POST {apiBaseUrl}/builder/staff-session` → `{ token, expiresAt, staff: { id, name, role } }`, or Django's 400 `{ code: 'invalid_ticket' }` returned as it is) and seals the answer in its OWN cookie, `__Host-builder-session` (`BUILDER_SESSION_COOKIE`): HttpOnly, Secure, SameSite=Strict, `Path=/`, `Max-Age` the time left to `expiresAt`, sealed through `nuxt/server`'s `getSession`/`updateSession`/`clearSession` with the key `nuxt/server` derives from `appSecret` for that cookie name. The browser is told `{ staff, expiresAt }`, never the token; `GET` answers the same or 401, `DELETE` revokes the token at Django (`DELETE {apiBaseUrl}/builder/staff-session`, StaffBearer; a 401 or 404 counts as already revoked) and expires the cookie (204; if Django cannot be asked the cookie is still expired and the request then fails). `requireBuilderStaff(event)` is what every future `/api/builder/**` route calls: 401 without a live session, else `{ staff, expiresAt, headers: { Authorization: 'StaffBearer <token>' } }` to pass on the Django call. Reading never mints a cookie (`readBuilderSession` checks the cookie first), and a cookie that holds no live session is expired. **Only `server/api/builder/**` and `builderSession.ts` may name the session, and no builder route is cached**: the SSR and handler caches hold anonymous renders (`test/unit/source-rules/builder-session-is-private.spec.ts`).
- `server/api/builder/preview-links/**` and `server/api/builder/shared/[token].get.ts` — share-preview links. Staff routes: `GET` lists the open links (no token), `POST { documents, note? }` freezes the SAVED drafts of the documents named (the page and its groups, `BUILDER_PREVIEW_MAX_DOCUMENTS`) behind a link and answers `{ token, id, ... }` once, `DELETE <id>` revokes. The public route opens a link: `GET /api/builder/shared/<token>?page=<slug>` asks Django's `builder/preview/<token>/<slug>` (the token is the only credential; no staff session is read) and answers `BuilderPreviewResponse` through `builderPreviewOf` (`server/utils/builderPreview.ts`, shared with the editor's `preview.post.ts`): the page under `page:<slug>`, the menus from the groups. Never cached, `X-Robots-Tag: noindex, nofollow`; Django's 404 `preview_link_expired` / `page_not_published` come back as they are. The page that shows it is `app/pages/_builder-preview/[token].vue` at `/_builder/preview/<token>?page=<slug>` (surface `share`, `builderSurfaceOf`): it puts the answer in `useBuilderCanvasPreview` and mounts the body the store serves that page with (`builderShareBody`), so every design draws it. The directory starts with an underscore so it is no reserved custom-page slug; the path is set by `definePageMeta`.
- `server/api/builder/media/**` — the media library for the editor's image picker (`BuilderMediaField` / `BuilderMediaPicker`, the `media` field kind of `builderSettingsFields`): `GET` lists (Django's paging, `search`, `ordering`), `POST` uploads (multipart, STREAMED through `proxyRequest` like the contact attachment, so its reply is Django's verbatim, a 5xx excepted (`refuseUpstreamFault`), and is marked `private, no-store` after Django's headers are copied), `[id]` `GET` / `PATCH` (alt text per language, focal point) / `DELETE` (a used image is Django's 409 `media_in_use` with `usedBy`, returned as it is). Staff only, never cached. A `media` ref is a data kind like the others (`DATA_RECORD_KINDS`): the public read is the cached function `builderDataMedia` over `GET builder/media/resolve` (only assets a current release uses; ids split at `DATA_MEDIA_MAX_IDS`; the language travels as `locale`). The editor's preview alone passes the staff member's credentials down (`BuilderReadOptions.staffHeaders`, from `preview.post.ts` through `resolveBuilderData` to the loader), which reads `builder/media/staff-resolve` instead, UNCACHED, so a draft shows an image nobody has published and no entry can hand it to a visitor. A share link has no staff session: it reads its images through its own token (`BuilderReadOptions.shareToken`, Django's `builder/preview-media/<token>`, which serves only the assets its frozen documents reference), also uncached. `builderDataMedia` is not yet in Django's `core/cache/surfaces.py`: the epoch in its key and its short TTL evict it until the block change adds the purge.
- `server/api/builder/presence/**` — the editor's soft "who else is editing" signal: `POST { documents }` is a heartbeat (the full list of documents open; ones left out are let go of) and answers `{ documents: { key: [{ id, name, since }] } }`, the caller excluded; `DELETE` lets go of all. The editor beats every `BUILDER_PRESENCE_HEARTBEAT_MS` (a third of Django's `BUILDER_PRESENCE_TTL_SECONDS`) from `BuilderPresenceNotice` (store `builderPresence`), shows the notice, and leaves on `pagehide`/unmount. A hint only: the draft's `If-Match` revision decides a save, and a failed beat shows nothing. Staff only (any role), never cached.
- `server/api/builder/documents/[key]/versions/**` and `checkpoint.post.ts` — a document's version history for the editor's panel (`BuilderVersionHistory`, store `builderHistory`): `versions` lists a page (`BUILDER_VERSIONS_PAGE_SIZE`, newest first) of the saved (`checkpoint`) and published (`publish`) versions, `versions/<n>` reads one with its content, `versions/<n>/restore` puts it back as the DRAFT against `If-Match` (409 `revision_conflict` returned as it is and handed to the editor's conflict dialog through `useBuilderAutosaveStore().reportConflict`; never the live page), `checkpoint` is a named save of the current draft. The draft and the live version are the document's own state, not list entries. Staff only, `private, no-store`.
- `server/api/builder/publish.post.ts`, `publish/check.post.ts` and `schedules/**` — publishing from the editor (`BuilderPublish`): `publish` releases the named documents' drafts together (`{ documents, note }` → the Release, or Django's 400 `invalid_document` with every problem by document: the generated `zBuilderDocumentInvalidError`, the third branch of every builder 400 that checks a document, which the autosave reads too); `publish/check` says what that would do, writing nothing (`{ ok, changed, problems }`), and the editor asks it after `useBuilderAutosaveStore().settle(keys)`, since both read the drafts Django holds; `schedules` lists (`?status=`), creates (`scheduledFor` with an explicit offset: the store's timezone is not exposed), cancels (`DELETE schedules/<id>`, 409 `schedule_not_pending` once it ran) and acknowledges a failed one (`POST schedules/<id>/acknowledge`). A failed schedule's `failure` is the problems it met (`PublishProblem[]`). Staff only, `private, no-store`; Django lets ADMIN and OWNER publish, so STAFF see no button.
- `server/api/admin/cache/purge.post.ts` — Django's purge of the Nitro caches (`X-Cache-Purge-Token`). Besides `patterns` it takes `builderDocuments` (`template:home`, `page:summer-sale`, `group:header`, `theme`): the documents a change reached, from Django's dependency rows. The storefront turns them into keys because it owns the routes (`builderDocumentMatchers`, `server/utils/builderDocumentPurge.ts`): a template or page purges the rendered pages at its address in every locale (matched on the key's first segment, Nitro's 16-character path escape), a section group purges every page and the chrome's menus (`builderChrome`), the theme and a template no route draws purge every page. A page or template document is named because a record it shows changed (Django's `builder.data_purge`), so the same request first drops the store's cached record data (`builderRecordDataMatchers`: `builderDataProduct`, `Category`, `BlogPost`, `BlogCategory`, `Promotion`, `Slug`; not `Media` or `Targets`, which no record change touches), then the pages, and answers after both: a render after the purge reads Django instead of storing the old list again. A theme or group document, or a purge of patterns alone, drops no data. What it cannot close: a page render already in flight when the purge lands read the old records, and the page it stores after the purge is an ordinary entry of the route cache. That page is served as fresh for its route's `swr` lifetime (the route rules: 300 s for `/`, `/offers` and the catalogue (`/products`, `/products/**`); 600 s for the blog (`/blog`, `/blog/**`), `/info/**`, `/loyalty-program` and the custom pages, `CUSTOM_PAGE_SWR_TTL`; 3600 s for the brand pages of `PRERENDERED_ROUTES`, `/about`, `/contact` and `/vision` among them), then served once more while Nitro re-renders it (`swr: true` with no `staleMaxAge`, so a stale entry has no age limit until a request comes). The next record change purges it again, and the first request after that lifetime replaces it. The 60 s data TTL bounds only the record-data entries, never that page. It takes more, never less, and always within the purged store (`host`).
- `server/api/texts/catalogue.get.ts` and `validate.post.ts` — the text catalogue of the build and the check of a store-written text against it (`server/utils/textCatalogue.ts`, `textValidation.ts`; the catalogue is the `#text-catalogue` virtual module from `modules/text-catalogue/`). Public and tenant-free: bypassed in `0.tenant.ts`, no `tenantCacheKey`, no Nitro cache (each view is a bundle constant served with its content hash as ETag, so the ETag varies by view). `catalogue?schema=<schema>` (`ZodTextCatalogueQuery`, an identifier) lists only the namespaces that store's storefront renders plus `global` (`modules/text-catalogue/reachability.ts`: a schema with a variant tree has its own view, any other, unknown ones included, gets the `default` one; without `schema` it is every text of the build, for tooling). `validate` takes the same optional `schema` and answers `unknown_key` for a namespace that store does not render; it answers 200 `{ ok: true }` or 422 `{ ok: false, code, detail }` with `code` one of `TEXT_VALIDATION_CODES`
- `server/api/texts/overrides.get.ts` — the store's own edited texts for a language, `{ namespace: { key: text } }` as Django stores them. Tenant-scoped (`tenantCacheKey` + the language), cached as the handler named `textOverrides`: Django's purge after a text edit names it (`cache:nitro:handlers:textOverrides*`, `core/cache/surfaces.py`), so renaming it stops edits reaching visitors until the TTL runs out. Unlike the catalogue it goes through `0.tenant.ts`
- `server/api/builder/catalogue.get.ts` — the page builder's block catalogue of the build (`server/utils/builderCatalogue.ts`; the `#builder-blocks` virtual module from `modules/builder-blocks/`): `{ hash, blocks: [{ type, version, accepts, schema, translatable, refs, limits, children, kinds, groups?, templates?, feature?, deprecated?, presets? }] }` (`presets`: what the editor's library inserts, a `default` on every block it offers, its text in the editor labels), `schema` the settings as closed JSON Schema (draft 2020-12, the INPUT type, so a field with a default may be absent). Django validates every builder save against it. Public and tenant-free like the texts catalogue (bypassed in `0.tenant.ts`, no `tenantCacheKey`, no Nitro cache); the content hash is the ETag (`Cache-Control: public, no-cache`, 304 on `If-None-Match`). `?schema=<design>` (the store's tenant schema) answers the catalogue of what THAT design draws: a block or page type that exists for other designs only (`designs` on `defineBlock`, on `STATIC_LAYOUT_ROUTES`) is left out, so Django, which asks per store, refuses it on save, and the editor's library never offers it (`builderLibraryOffers` takes the design); the hash and ETag are that view's own, and without a schema it is the whole build's catalogue with each block's `designs` stated. `test/unit/source-rules/block-designs.spec.ts` keeps the declaration and the component registry in step (a design-only section has a `<type>@<design>` entry and no base entry; a section with no base entry names its designs). `accepts` is the current version alone: Django holds only this schema, and an older node is upgraded on read (`upgradeNode`, `shared/builder/upgrade.ts`) and by the editor on load. `documentKinds` states what a kind of document carries at its root (`shared/builder/documentRoots.ts`: a page's and a template's SEO copy, the model's limits, and its `heading` (`BUILDER_PAGE_HEADING_MAX_LENGTH`; the editor offers it on `BUILDER_HEADING_DOCUMENTS` only), all translatable; the theme (`zThemeSettings`, `shared/theme/settings.ts`): a light and a dark scheme, each with three colours and their stored OKLCH scales, the main action colour (`--ui-primary`) and whether picking a primary sets it (`actionLinked`), the accent (`--ui-secondary`), the status colours and the heart, then the radius, faces and page width, every key required; per DESIGN (`builderDocumentRootsFor(schema)`, `resolveDesign`), `contrast`: the WCAG 2.2 pairs that design paints with and a store can break (`themeContrastRulesFor`: on webside body text, an `error` Django refuses a publish on as `insufficient_contrast`, and muted text; on Groove Volt, whose surfaces are fixed design tokens, only the action and accent colours against its background; evaluated by `shared/builder/contrastRules.ts`, both sides held to `test/fixtures/builder/contrast-cases.json`, every token a rule names held to its design's stylesheet by `test/unit/shared/builder/documentRoots.spec.ts`), and `defaults`: the theme a new store of that design starts with (`themeDefaultsFor`, exactly what the design renders for a store that changed nothing; Django writes it as the store's first theme); a group carries none) and `templates` lists the page types the storefront's static routes render (`STATIC_LAYOUT_ROUTES`: a layout of one is the document `template:<pageType>`, any other the custom page `page:<pageType>`); both are part of the hash. With no block defined `blocks` is empty, and Django then refuses every save.
- The document pipeline is SHARED, so the server and the page editor run one implementation (`shared/builder/`): `document.ts: parseDocument(raw, kind, registry, { featureOn, onSkip })` (a page's root `settings` too, against `BUILDER_DOCUMENT_ROOTS[kind]`; a block whose store `feature` is off is left out as `feature_disabled`, so turning a feature off never leaves a dead section on a live page: the server passes `eventStoreFeature`), `props.ts: sectionProps(node, registry)` (the props the unchanged section component gets), `links.ts: collectLinkRefs` / `resolveLinks` and `navigation.ts: navigationItems`. Each takes the block registry: the server passes `builderBlocks` (`server/utils/builderCatalogue.ts`), the editor `builderEditorBlocks`. `parseDocument` upgrades each node to its block's current version, validates its settings against the block's schema and REBUILDS it from the parse (unknown keys never survive), checks kind, allowed children and the three-level depth cap, and leaves out a node it cannot use, children with it, reporting each to `onSkip`; the server's routes pass `logSkippedNode` (`server/utils/builderDocument.ts`: `log.warn({ tag: 'builder', message: 'node skipped', node, reason, detail? })`). It never throws for one bad node; a document that is not one is an empty document. Only the editor's chunk imports the block definitions in the browser, so no schema reaches the public pages. The reads from Django stay on the server: `readLinkTargets` (`server/utils/builderLinks.ts`: the slugs and the published pages a page's links name, each a cached function of its own, `builderDataSlug` and `builderDataTargets`, so a renamed record is linked at its new slug within a minute and a purge reaches it at once), `readPublishedSummary` / `publishedTargets` (`server/utils/builderTargets.ts`, by store and language rather than by request, so a cached function can make them).

## OpenAPI Type Generation

Types and Zod schemas are auto-generated from the Django backend's OpenAPI schema:
1. `pnpm generate:schema` — fetches `openapi/schema.json` from Django (`scripts/fetch-schema.mjs`; sends `DJANGO_API_TOKEN` as a Bearer token when set, which a local Django with `DEBUG=True` does not need). Reads **`NUXT_DJANGO_URL`** (default `http://localhost:8000`) — point it at LOCAL Django, never prod: prod's `/api/v1/schema` is a subset (255 components vs 271 local) and regenerating from it silently deletes components the frontend uses (`Country`, `BlogAuthor`, `Paginated*List`).
2. `pnpm openapi-ts` — generates `shared/openapi/types.gen.ts` and `shared/openapi/zod.gen.ts` via `@hey-api/openapi-ts`
3. `pnpm sync:schema` — **required, not optional.** `openapi/schema.yml` and the root `schema.yml` are derived from `openapi/schema.json` by `scripts/sync-schema-yml.mjs`. CI's *OpenAPI Schema Freshness* job regenerates them and fails on any diff. Copying Django's `spectacular` YAML across directly also fails it — the YAML dump formatting differs.

**The allauth document.** allauth's headless API (`/_allauth/app/v1`, which `server/api/_allauth/` proxies) is a second input: Django commits its OpenAPI document as `allauth-schema.yml` at its repo root (`manage.py allauth_schema`, `docs/allauth-schema.md` there), and `pnpm sync:allauth-schema` copies it, byte for byte, to `openapi/allauth-schema.yml` (the file the infrastructure's deploy gate reads). `pnpm openapi-ts` generates it to `shared/openapi-allauth/{types,zod}.gen.ts`, every name prefixed (`AllAuth…`, `zAllAuth…`; operations are `z<Method>AllauthAppV1<Path>Body|Response|Headers`, e.g. `zPostAllauthAppV1AuthLoginBody`) by the naming hook in `openapi-ts.config.ts`, so nothing collides with Django's own schema in the auto-imported `shared/` name space. A route under `server/api/_allauth/` validates its body and response with the operation's generated schema; where the document gives an operation no 2xx (logout, login-code request, password change, passkey signup start: Django answers 401) the route has no success branch. Error bodies have no generated Zod except the component schemas, so `shared/utils/allAuthErrorGuards.ts` classifies them with those and by status for the 404 (TOTP setup) and 429. The names the storefront composes from them are in `shared/types/allAuth.ts`. A gap between the document and a real answer is fixed in Django's document, never by loosening or extending the generated schema here.

Commit `openapi/schema.json`, both `schema.yml` files, `openapi/allauth-schema.yml` and `shared/openapi/*` + `shared/openapi-allauth/*` together. A removed field is the dangerous direction: the committed Zod still marks it `required`, so `parseDataAs` rejects the correctly-absent field with a 422, and only on the one flow returning that nested object.

## Shared Code (`shared/`)

Auto-imported in both app and server contexts (via `imports.dirs` and `nitro.imports.dirs`). Contains:
- `types/` — Hand-written types organized by domain: `allAuth.ts` (the storefront's names over the generated allauth types), plus `pagination.ts`, `search.ts`, `meilisearch.ts`, `LoyaltySettings.ts`, `enum/`, `utility/`
- `schemas/` — Hand-written Zod schemas for what no generated schema describes (`allAuthTotpSvg.ts`: Django's own TOTP setup view, not in either document)
- Nothing in `shared/` imports Vue or Nuxt UI (`#ui/types`): Nuxt forbids it, and with typed `$fetch` it pulls the app's whole type graph into the shared context. UI-only types live in `app/types/` (the dynamic form schema, ordering options).
- `openapi/`, `openapi-allauth/` — Auto-generated `types.gen.ts` and `zod.gen.ts` (Django's API, allauth's API)
- `constants/` — `Flow2path`, `AuthChangeEvent`, `GSIAuthProcess`, `RedirectToURLs`, `Flows`, `AuthenticatorType`, `defaultSelectOptionChoose`
- `utils/` — `error.ts` (error helpers), `html.ts` (HTML processing)
