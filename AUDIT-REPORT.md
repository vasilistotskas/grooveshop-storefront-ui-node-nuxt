## ⚠ ACTION REQUIRED — production secrets leaked into published artifacts

The CI release pipeline (`.github/workflows/docker.yml` + `ci.yml`) writes the **real** `NUXT_SESSION_PASSWORD`, `NUXT_SECRET_KEY`, and OAuth client secrets into `.env` at build time. `.env` is **not** in `.dockerignore`, so `COPY . .` pulls it into the build and Nuxt bakes those values into `.output/server` as runtimeConfig defaults — which is then pushed to Docker Hub + GHCR and attached to every GitHub Release as the `.output` asset. ## High-severity findings (23)

### H1. 5-star fill rendered from 10-point reviewAverage without dividing by 2 — most products show full 5 stars ✅ FIXED

- **Where:** `app/components/Product/Card.vue:255`  ·  _correctness_
- **Evidence:** Card.vue L251-257: `<UIcon v-for="star in 5" :name="star <= Math.round(product.reviewAverage) ? 'i-heroicons-star-solid' : 'i-heroicons-star'" ...>`. Ratings are on a 1-10 scale: `shared/openapi/types.gen.ts:5991 export type RateEnum = 1|2|...|10`, Review.vue zod `rate: z.number().min(1).max(10)`, PDP schema.org `bestRating: 10`. The shared `app/components/Rating.vue:21` does `const fullStars = Math.floor(productRate / 2)` — Card.vue omits the /2, so any product with average >= 4.5/10 rounds to >= 5 and paints all 5 stars solid.
- **Impact:** Every product listing surface (products list, favourites, search results render ProductCard) shows misleading star ratings — a mediocre 5.0/10 product displays a perfect 5/5 star row next to the numeric '5.0', misrepresenting product quality to shoppers.
- **Fix:** Use the 10→5 conversion consistent with Rating.vue: `star <= Math.round(product.reviewAverage / 2)` (or reuse the Rating component).

### H8. Scheduled checkout retry is blocked by its own isSubmitting guard, leaving checkout stuck in loading forever ✅ FIXED

- **Where:** `app/composables/useCheckoutSubmit.ts:296`  ·  _state-machine-deadlock_
- **Evidence:** handleRetryableError keeps the flag set: line 295 `isSubmitting.value = true`, then lines 296-299 schedule `retryTimeoutId.value = setTimeout(() => { retryTimeoutId.value = null; onSubmit() }, 500)`. onSubmit line 514: `if (isSubmitting.value) return` runs BEFORE the try block. The finally block (lines 602-615) only resets isSubmitting `if (!retryTimeoutId.value)` — at finally time the timer IS pending (the $fetch rejection that triggered onResponseError resolves immediately, well within 500ms), so isSubmitting stays true. When the timer fires, the re-entrant onSubmit hits the line-514 guard and returns without doing anything, and nothing ever resets isSubmitting. The sidebar CTA (app/pages/checkout/index.vue:398 `:loading="isSubmitting"`) spins forever; the user must reload. - **Impact:** The only retryable error class (expired stock reservation) permanently deadlocks the checkout submit button — direct revenue loss under a realistic condition (shopper idles >15 min, then submits).
- **Fix:** In the setTimeout callback, reset isSubmitting before re-entering: `retryTimeoutId.value = null; isSubmitting.value = false; onSubmit()`. Also reset retryCount to 0 at the top of a fresh (non-retry) onSubmit or on success in all three flows.

- **Evidence:** backToForm (lines 664-669) only resets `createdOrder.value = null`, `selectedPayWay.value = null`, `currentStep.value = 2`. - **Fix:** On backToForm: clear paymentIntentId/idempotencyKey and either (a) navigate to cart with an explanation because the cart was consumed, or (b) call a backend order-cancel endpoint that restores the cart, then refreshCart(). At minimum reset paymentIntentId so a resubmit mints a fresh PI.

### H10. Hosted-payment cancel/failure return path is unreachable: the cart is consumed at order creation, so ?canceled=true returners are bounced to home as 'cart empty' with no notice and no retry path ⏸ DEFERRED

> **DEFERRED — hosted-payment cancel/failure path needs a backend flow that restores or re-associates the consumed cart, or a dedicated retry-against-pending-order page.**

- **Where:** `app/pages/checkout/index.vue:26`  ·  _payment-state-machine_
- **Evidence:** Lines 23-41: the page expects Stripe/Viva to 'redirect back to this page with ?canceled=true or ?error=<code>' and shows a toast in onMounted. But for hosted flows the order (and thus the cart — Django deletes it on order creation, grooveshop-django-api/order/signals/handlers.py:176-222) already exists before the shopper is sent to the provider. ### H11. Revisiting a success URL (history/bookmark) wipes the shopper's current cart — cleanCartState keys off query params that persist forever ⏸ DEFERRED

> **DEFERRED — needs a per-order idempotency guard (compare the order's cart id, or a one-shot token) so revisiting the success URL never wipes a new cart.**

- **Where:** `app/pages/checkout/success/[uuid].vue:240`  ·  _cart-integrity_
- **Evidence:** Lines 14-24 derive `fromCheckout` purely from URL query (`session_id`, `s`, `placed=1`) which persists in browser history and bookmarks. So a guest who completed an order, later builds a NEW cart, then reopens the success page from history (to check the order number/tracking) has the new cart's session binding destroyed — the cart id is unrecoverable and the items are lost. - **Fix:** Only clear when the current cart is actually the one consumed by this order (e.g. compare a cart identifier stored on the order, or pass a one-shot flag via sessionStorage/router state that is consumed on first arrival), and fix the stale comment.
